How the TypeScript under src/ is arranged: which tier each folder belongs to, the order of subfolders inside large folders, and what each subfolder role means.

This page is the human copy. The same content for the assistant lives in docs/code-layout.md; update both together. .dependency-cruiser.cjs enforces every order on this page (make lint).

The one rule

src/ has three levels: tiers, folders and, in large folders, subfolders. At every level the parts run in one line, lowest first, and a part may import only the parts before it (and anything in earlier tiers). Files in the same subfolder, or in a folder without subfolders, may import each other freely. Import cycles are never allowed.

  • A folder with 10 or more source files gets subfolders. Such a folder keeps no files of its own: every file, including its main file, sits in a subfolder.
  • Subfolders are split by role first (pure, then glue, then components) and by domain concept second.
  • Folder names carry no numbers; the order lives in .dependency-cruiser.cjs.
  • Tests sit beside the code they test. Inside a folder a test may import later subfolders to set up its scenario (shipped code may not); tests still keep the tier and folder order. src/testSupport/ sits outside the tiers; only tests may import it.

TierWhat it holds
coreThe domain model and the reaction and track file formats. Pure, shared by everything.
drawingTurning states into SVG drawings. Pure.
learnerEverything the learner site needs, from a step session to the Svelte app. Never reaches RDKit.js or Node.
toolingRDKit.js and the Node tools that check, build and push content.
createThe authoring decisions and the Create app.
serverPostgres and the HTTP server.

Tooling sits above learner on purpose: the tier order alone keeps RDKit.js, the linter, Create and the server out of the learner site.

Subfolder roles

In the two apps (learnerSite/, reactionEditor/)

modelPure TypeScript: decisions, view text, routes, and the interfaces that io adapters satisfy. No DOM, no fetch, no storage.
componentsSvelte that renders what it is given and reports what the user did through callbacks. May use model. No I/O, owns no task.
ioTalks to the outside world (fetch, storage, cookies, the lint worker, focus): the adapters, and for now files that mix pure logic with I/O.
workspacesSvelte that owns one task (a run through a reaction, a stage of a draft). Combines components; may use io.
pagesWhat the app routes to. Loads what it needs; hosts workspaces and components.
appThe root component, routing, the entry point, index.html and the site CSS.

Highest at the top. components sits below io, so the import rule itself stops a component doing I/O.

Shared by other folders

RoleWhat it holds
modelThe pure types, errors and rules of a folder that is mostly I/O (e.g. reactionDatabase/model/).

Every other subfolder is named after its domain concept (rules/, scheme/, mechanism/, …).

Placement notes

  • coordinateSeeding.ts (laying out a state's 2D coordinates with RDKit.js) lives in tooling/chemistryToolkit/: both the linter's seed-coordinates command and reactionEditing use it, so it must sit below both.
  • stateAtomConsistency.ts lives in tooling/reactionLinting/ (its only user), so core/ never needs RDKit.js.
  • lintRequests.ts (the lint worker's request protocol) lives with the worker in reactionEditor/.
